2. Choix du projet : EniGov (objectif 1)

2.1 Présentation

EniGov est la plateforme numérique de gouvernance étudiante de l’ENICarthage (dépôt : github.com/Mahmoud35amri/EniGov). Le délégué élu y publie des annonces, gère les réclamations des étudiants, organise des sondages, publie des décisions et des événements, partage des documents et échange par messagerie. Les étudiants, inscrits avec une adresse @enicar.ucar.tn, consultent ces informations, déposent des réclamations (privées ou publiques), votent et écrivent au délégué.

2.2 Pourquoi ce projet ?

  • Application réelle et complète : backend Java, frontend React, base de données, authentification ; tous les niveaux de test s’y appliquent.
  • Deux rôles (DÉLÉGUÉ, ÉTUDIANT) avec des règles d’accès : terrain idéal pour les tests de sécurité et d’autorisation.
  • Règles métier testables : vote unique, ciblage des sondages, verrouillage après 5 échecs, politique de mot de passe (valeurs limites, tables de décision).
  • Données sensibles : réclamations privées, d’où des exigences de confidentialité à vérifier.

2.3 Architecture technique

CoucheTechnologies
FrontendReact 18, Vite 5, React Router 6, Tailwind CSS, Axios, Framer Motion
BackendJava 17 (exécuté sur JDK 25), Spring Boot 3.2.2, Spring Security + JWT (jjwt 0.11.5), Spring Data JPA / Hibernate
Base de donnéesPostgreSQL (schéma généré par Hibernate : ddl-auto=update)
Services externesCloudinary (fichiers), Brevo (e-mails) — non configurés en local

5. Outil de gestion des tests et des exigences : Squash TM (objectif 3)

5.1 Choix de l’outil

Squash TM est un outil libre de gestion des tests qui gère dans un même référentiel les exigences, les cas de test et les campagnes d’exécution, avec la traçabilité entre eux. Il répond donc à la consigne : simplifier la gestion des tests tout en gérant les exigences du logiciel. Il est en français, gratuit en version Community et s’installe sous Docker.

5.2 Organisation du projet EniGov dans Squash TM

  • Exigences : 27 exigences réparties en deux dossiers (fonctionnelles / non fonctionnelles), avec catégorie, criticité et statut « Approuvée ».
  • Cas de test : 33 cas répartis en six dossiers : « 01 - Tests unitaires (JUnit 5 + Mockito) », « 02 - Tests d'intégration (Spring Boot + MockMvc + PostgreSQL) », « 03 - Tests système (E2E Playwright) », « 04 - Tests d'acceptation (manuels) », « 05 - Tests non fonctionnels », « 06 - Tests liés aux changements et de maintenance ». Chaque cas a une nature, un type, une importance, des pas de test (action → résultat attendu) et un lien vers les exigences qu’il vérifie.
  • Campagne « Campagne de recette EniGov v1.0 » avec deux itérations : build initial v1.0.0, puis build corrigé v1.0.1.

Pour éviter une saisie manuelle de plus de 30 cas de test, le référentiel a été écrit une seule fois (qa/squash/referentiel.mjs), puis injecté dans Squash TM par son API REST (script qa/squash/seed.mjs). Le même fichier sert à générer les tableaux de ce compte rendu, ce qui garantit leur cohérence.

7.1.2 Analyse statique du backend (PMD / CPD)

Aucune violation de priorité 1 ou 2. Les points notables : trois blocs catch vides (des erreurs d’envoi d’e-mail sont silencieusement ignorées), UserDetailsImpl redéfinit equals() sans hashCode(), des imports inutilisés et 8 blocs dupliqués de 10 à 17 lignes.

7.1.3 Analyse statique du frontend (ESLint)

Répartition : 34 variables ou imports inutilisés, 19 caractères non échappés dans le JSX, 2 dépendances manquantes dans des useEffect (risque de données obsolètes à l’écran), 2 attributs inconnus. Ces défauts relèvent de la dette technique (ANO-07).

7.1.4 Analyse des dépendances (npm audit)

29 vulnérabilités connues : 15 hautes, 11 modérées, 3 faibles. Elles touchent notamment axios (SSRF, contournement d’authentification) et react-router (redirection ouverte). L’exigence ENF-08 n’est pas satisfaite (ANO-06).

7.4 Tests structurels (couverture de code avec JaCoCo)

Le plugin JaCoCo instrumente le bytecode pendant mvn test et mesure les instructions et les branches exécutées par les tests unitaires et d’intégration.

Analyse : l’objectif de 40 % des instructions est atteint (49 %). La couverture est concentrée sur les modules à risque P1 (réclamations 77 %, sondages 60 %, sécurité 91 %). Les services de messagerie, d’annonces et d’événements sont surtout exercés par les tests E2E, que JaCoCo ne mesure pas dans cette configuration. La vue détaillée montre aussi des branches non exécutées : getAllComplaints n’est appelée par aucun test JUnit, ce qui indique les prochains tests à écrire.

7.7 Tests non fonctionnels

Performance et fiabilité : test de charge k6 (TNF-01)

Profil de charge : montée à 20 utilisateurs virtuels en 10 s, palier de 40 s, descente en 10 s. Chaque utilisateur consulte cinq ressources (annonces, événements, sondages, réclamations, statistiques), puis marque une pause d’une seconde. Seuils : p(95) < 500 ms (ENF-03) et taux d’échec < 1 % (ENF-04).

Résultat : 4 631 requêtes (56 req/s) ; temps de réponse moyen 18,8 ms, p(95) = 35,7 ms, maximum 247 ms. Une seule requête a échoué (0,02 %), sur un délai réseau entre le conteneur k6 et l’hôte (i/o timeout), et non sur une erreur applicative. ENF-03 et ENF-04 sont satisfaites avec une large marge.

7.8 Tests liés aux changements et tests de maintenance

Correctifs appliqués

Les deux anomalies corrigeables sans changement de conception ont été corrigées : ANO-01 (contrôle du propriétaire dans ComplaintService.getById) et ANO-02 (interception de SecurityException dans JwtUtils).

Re-test de confirmation (TR-01) et non-régression (TR-02)

Le re-test ré-exécute les cas qui avaient échoué (TU-04, TI-05) pour confirmer la correction. La non-régression ré-exécute toute la suite automatisée (52 tests JUnit et 7 tests E2E) pour vérifier que les modifications n’ont rien cassé. TI-09 (ANO-03, non corrigée) est désactivé avec @Disabled et une justification, puis marqué « Bloqué » dans Squash TM.

La vue source JaCoCo (figure 15) montre que le nouveau code du correctif ANO-01 est entièrement exécuté par les tests (branches en vert).

Tests de maintenance (TM-01)

Le projet cible Java 17 et une base PostgreSQL locale. Il a été porté vers un nouvel environnement : JDK 25 et PostgreSQL 16 sous Docker. La compilation et l’ensemble des tests passent. Un seul ajustement a été nécessaire : Mockito/Byte Buddy 1.14 ne reconnaît pas officiellement le JDK 25, d’où l’option -Dnet.bytebuddy.experimental=true ajoutée au pom.xml. Une mise à jour de Spring Boot (≥ 3.5) supprimerait ce contournement.

9. Conclusion

Ces ateliers ont permis de mener une démarche de test complète sur une application réelle : de l’expression des besoins jusqu’au verdict de recette. Squash TM a centralisé les exigences, les cas de test et les campagnes. La matrice de traçabilité montre quelles exigences sont vérifiées, et par quels tests.

La combinaison des techniques s’est avérée efficace. La revue de code (statique) a trouvé les défauts les plus graves avant même l’exécution, et les tests dynamiques les ont confirmés et ont mesuré leur impact. Les tests automatisés (JUnit, Playwright, k6) rendent la non-régression peu coûteuse. Les tests manuels restent indispensables pour juger l’expérience utilisateur et explorer des comportements inattendus, comme la perte des événements au redémarrage. Enfin, le cycle correction → re-test → non-régression a été appliqué à l’anomalie critique de confidentialité, désormais corrigée.
